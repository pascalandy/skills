# Prototype

1. Choose fidelity. A **mockup** is polished and mostly static, for hierarchy and product fit. A **prototype** implements a bounded flow for navigation, input, state changes, feedback, or recovery. Record user, critical job, scenario, design source, and where the real product takes over. Finish when mode and boundary are explicit.
2. Before building, list reachable states. Simulated asynchronous actions need pending, success, and failure or recovery states. Collections need relevant empty states. Disabled actions need visible reasons. Include domain-specific states from the brief. Finish when every included state is reachable and relevant omissions have stated boundaries.
3. Build with realistic, consistent content. For prototypes, complete navigation and forms within scope, including labels, validation, defaults, and submission feedback. Label simulated outcomes. For mockups, state the static boundary and preserve semantic structure. Finish when every control works within the flow or is clearly outside the static review's scope.
4. Run shared verification and test every state. For dialogs, check accessible names, focus containment, Escape dismissal, and focus restoration. Associate form errors with controls. Announce important status changes. Test Tab, Shift+Tab, Enter, Space, and applicable arrow keys. Check long content and disabled actions. Finish when keyboard and pointer work at both widths, or the handoff names unavailable checks.

Return fidelity, scenario, implemented states, and excluded production behavior.

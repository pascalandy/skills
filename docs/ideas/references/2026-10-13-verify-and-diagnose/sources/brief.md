## Who asked and what they want

Pascal (the user) read the post and believes it holds several skills, not one. In his words, roughly:

- The post opens with how to do an adversarial review well, with many principles: the full workflow, finding the root cause, avoiding the trap of taking the first answer for the real answer, managing all hypotheses as a matrix
- It then covers the "software factory": how to build the whole solution so it is easy to debug. He sees that as another skill. There is probably more
- Goal 1, build time: when building software, each feature or group of features should add hooks to the verification loop. Each new feature should be easy to test and to trace back
- Goal 2, run time: the code is in prod, a bug arrives. Gather all the signal from the bug, then apply the framework
- He does not want to stop at these two. Propose better ideas

His meta-request, verbatim: "Think deeply about how to make this entire system as agent-intuitive, agent-ergonomic, and agent-accretive as you can possibly imagine. Put yourself in the driver's seat and imagine that YOU are the one using this system and driving it. What would most enable you to do an awesome job understanding the situation accurately and optimally controlling everything to drive the best and most accurate results possible, with the least expenditure of resources? [...] Don't just think of the project as an assemblage of various parts or components: really try to profoundly and deeply conceptualize it as a synthetic SYSTEM that is maximally coherent, cohesive, modular, and interconnected, forming a tower of linked abstractions that are maximally legible to you as an agent."

"Agent-accretive" means: each use of the system leaves it stronger, so the next agent starts further ahead (the post's "every human intervention is a gap to close", "turn skill issue into infrastructure issue", "decision points become policy").

His standing preferences: ambitious ideas, simple systems, smallest model that makes correct behavior unsurprising. Measure twice, cut once, and YAGNI. DRY; prevent drift. E2E tests over unit tests. Fight scope creep. No machinery for its own sake.

## What to produce

Write your design to the output path your task names, in Markdown. Read-only everywhere else. No commits, no edits to either repo.

Your design must cover:

1. **Knowledge extraction.** Every distinct, actionable idea in the post, as a numbered list of principles, each one sentence plus where it applies. Mark which are novel relative to the existing skills above and which already exist there
2. **The system.** The tower of abstractions: shared vocabulary, shared artifacts (data shapes an agent reads and writes), skills, playbooks, scripts, and how control and data flow between them. Show the layers explicitly. Say which single concept the whole tower rests on
3. **Skill inventory.** For each proposed skill or playbook: name, location (repo/category, or a route inside an existing mode), trigger description (the frontmatter `description`, written as a trigger), purpose in one line, inputs, outputs, the artifact it reads and writes, the other skills it calls or is called by. Prefer fewer, deeper skills. Justify every new skill against folding it into an existing one
4. **Artifacts.** Concrete schemas (Markdown or JSON) for whatever the agent maintains during work, such as a fact ledger or a hypothesis-by-fact matrix. Say who may write which part (the post says facts are immutable to the agent)
5. **Goal 1 (build time)** and **Goal 2 (bug in prod)** walked end to end as an agent would run them, step by step, naming the skill and artifact at each step
6. **Accretion.** How each run makes the next one cheaper: where lessons, signals, controls, and policies land, and who reads them next time
7. **Changes to existing skills.** A list of edits, each with file path and the reason; flag any conflict between the post and an existing skill, and recommend a resolution
8. **Evals.** Use the post's three bugs (latency, memory leak, hang) as eval scenarios: what a correct agent does at each step, and what failure looks like
9. **Phased plan.** What to build first for the most value, in small verifiable units; what to defer or reject (YAGNI)
10. **Open questions** only Pascal can answer

Be concrete and opinionated. Prefer one strong recommendation over a survey of options.
